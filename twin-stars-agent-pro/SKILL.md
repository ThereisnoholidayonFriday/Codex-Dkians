# Twin Stars Agent Pro

以效率为主的独立流程：理解产品 → 定向快查 → 三方向各一张 → 用户选方向 → 整套制作与核心自检交付。与用户使用相同语言交流，不预设品类、平台、风格或画布。

本技能自包含。不要调用原版 Twin Stars 的六个流程技能、V6 CLI、状态机或旧项目控制文件；不自动迁移旧项目。默认一个主 Agent 完成，不建立固定子 Agent 团队。实际工具使用仍遵守当前工具说明；取消旧门禁不等于取消实际看图。

## 内置审美与方向控制

用户只需调用 `$twin-stars-agent-pro`。在需求解读、三案设计、实际样图和修图中默认执行[内置审美控制](references/aesthetic-control.md)：识别受众/渠道/品牌与参考图角色，把“高级、克制”等词或可选 1–10 强度参数转成可观察的焦点、构图、灯光、字体与信息层级，写入 `project.md` 的简短方向质量锁。三案在核心表达和视觉组织上真有区别；实际样图以目标尺寸核验硬约束和审美目标。修图明确缺陷、改动、保护项与复查点，仍遵守 Pro 的两次/资产预算。不新增 JSON、门禁、审批或独立评审。

Leonxlnx/taste-skill 的网页前端反模板化思路已在本 Agent 内按静态画面适配。**不要求用户另行调用** `$design-taste-frontend`，它也不是 Pro 的运行依赖；不要声称另一个技能独立审核过成品。若任务还包括真正的网页代码，Agent 可在自身入口下组织可用内部工具，但静态生图自检不能代替响应式、交互和无障碍检查；不把网页专属规则机械套进静态图。

## 1. 理解需求，定向快查

- 阅读用户材料中的文字、表格、注释和相关嵌入图，实际查看产品图片。提炼产品身份与可见结构、用途、受众、资产数量、尺寸、逐字文案、Logo、参考风格与限制。
- 用户明确的数量、风格、制作范围和授权优先于以下默认流程。用户只要 Prompt 时交付 Prompt，不启动生图；明确要求直接制作且已授权范围时，不强制再走三案与确认。
- 用户提供的产品信息记录为用户提供，不冒称独立核验。不因缺少额外外部佐证而新增常规审批。Agent 可提出创意和普通营销文案并直接用于样图，但不得自行添加产品参数、认证、销量、比较结论或功效事实；用户提供的逐字文案不得擅改。
- 只询问影响实际制作的关键缺失或冲突，每批最多三个问题；继续处理不依赖答案的部分。一般构图、配色、灯光和普通文案由 Agent 作出合理决定，不把创意工作退回用户。
- 围绕当前市场定位和三方向需要的视觉参考做一轮定向检索，必要时同轮打开相关来源。仅关键缺口允许补查；新信息不改变方向选择或制作决策时停止。把简短结论与来源链接写入项目记录，不写独立研究报告，不设置竞品或参考数量配额。不把审美参考当作畅销证据；无法联网时说明限制并基于已有资料继续可完成部分，不编造研究结果。

## 2. 三方向，各一张代表图

- 直接提出三个在核心表达、视觉组织或摄影/表现方式上有实质区别的方向。不做每方向四候选探索，不以换色、换名或换装饰冒充不同方向。
- 每方向用几句话明确表达重点、构图、光线材质、文字层级和套图延展规则。三张样图默认服务同一核心任务，使用相同目标规格和所需真实文案，便于比较；不另做三张/方向的主视觉、关键表达、难点样张。
- 为每张图准备一条自包含、模型中立的完整中文 Prompt，涵盖产品身份、场景与交互、构图、灯光材质、逐字图内文字、Logo、风格和目标尺寸。图内文字保留用户要求的语言；修改后交付更新后的完整 Prompt，不交付依赖旧上下文的补丁指令。
- 使用可用的内置生图工具，按其引用图片接口提供实际产品参考。整张画面一次包含产品、场景、人物（如需要）、文字、Logo 和版式，不改用分层拼贴流程。编辑已有图片前先查看实际图片。
- 目标尺寸是交付要求，不能仅写入 Prompt 就声称满足。查看实际输出尺寸，必要时按工具允许的方式安全适配并复查；工具无法满足的尺寸或文字要求如实标记未完成。工具不可用时保存 Prompt 与受阻说明，不默默切换外部付费模型或伪造图片。

## 3. 自检后，一次选方向

实际查看每张输出及其目标使用尺寸预览，集中检查：产品外观与结构、要求落实、逐字文字与 Logo、实际尺寸、明显接触/比例错误、视觉焦点和文字可读性。有问题时先使用剩余预算定向修正。不要求独立评审、盲评、自动 OCR、评分表或单独套图审查；工具辅助仅在能解决实际疑点时使用。

一次展示三张实际样图、简短差异与推荐，请用户确认方向和后续资产范围。确认范围应能明确剩余图片数量、用途、尺寸和必要文案。已有明确授权直接沿用，不重复询问。缺失或失败样张如实标记，其他已通过样张可供选择，不为凑齐三张超预算或阻塞可用范围。

用户选中且满足最终要求的样图直接计入成品，保留其资产身份与已用次数；单图任务可直接交付。未选方向留作候选，不算最终资产缺失。

## 4. 整套制作、修改与恢复

- 按选定方向制作剩余资产，完成同一核心自检，并在现有成品中检查套图风格与信息节奏的一致性；无需另开套图评审或交付确认。
- 每个逻辑资产最多两次实际生图工具调用：首次生成和一次定向编辑或重生成。实际发起后即计数，包括调用失败；确认未发起的不计数。每次调用只请求当前资产的一张候选，避免一次调用隐藏额外候选。
- 三个不同方向的首张样图各是一个资产；样图转成品、重命名、另存、重启或修订不创建新预算。真正新增的交付尺寸/用途可建立新资产，但不能把同一任务的失败重试改名为“扩图”。
- 调用前在项目记录中标记将要调用的资产与次数，返回后立即记录实际结果。恢复时核对真实工具历史；调用是否发生不确定时先保留为待核实且占用额度，不直接重试以规避上限。不把记录中的准备动作当作生图成功。
- 修正前用一句话写明可见问题、此次具体改动及需保护的已通过部分。修后检查目标和保护项，并复查该图核心质量。耗尽次数后保留候选、问题和可执行建议，继续其他资产，不自动第三次调用。
- 单图修改只处理该图；用户改变共享产品要求、文案或风格时，只重新检查实际受影响资产。继续已有 Pro 项目时先读项目记录、现有 Prompt 与当前图片，沿用选择、文件和预算，不重新研究、三案探索或确认已授权范围。

## 最小记录与交付

项目内只维护一份 `project.md`：需求摘要及材料路径、快查结论/来源、三方向摘要、用户选择与授权依据、简短风格规则，以及资产表。资产表记录稳定 ID、方向/用途、目标尺寸、当前图片与 Prompt 路径、已实际调用次数、真实工具结果引用（若工具提供）、状态和修改说明。状态用候选、待选择、已通过、未完成等易懂文字即可，无需 JSON 控制表、哈希绑定或审批命令。

使用项目内 `inputs/`、`work/`、`outputs/` 三个目录，按实际需要创建：保留产品参考与源材料、候选/历史版本，以及当前通过的成品。源材料不覆盖，替换成品前把旧版留在工作区；不建立审计包、品牌记忆库或强制复盘文件。品牌信息只在当前项目记录中保留，不声称已建立跨项目记忆。

交付当前选定范围的已通过图片、每图一份完整中文 `.prompt.txt`、对应产品参考图（同一参考可共享），并指向 `project.md` 中的简短风格与未完成项说明。交付前核对图片和 Prompt 对应、图内语言、尺寸及范围。未通过图片留在候选区；部分完成时明确缺项，不缩小清单后宣布整套完成。不得把未执行的检查、缺失的图片或未获用户认可的商业效果标为已通过。

若需评估提速，用同一真实任务记录实际生图调用数、用户确认轮次、过程文件数和总耗时。没有对照实测就不承诺提速百分比；格式验证不代表实际图片质量验收。
