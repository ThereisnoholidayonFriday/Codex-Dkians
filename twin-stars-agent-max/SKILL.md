# Twin Stars Agent Max

Turn product images and requirements into the requested static commercial visuals. Categories, channels, languages and sizes are open; use the actual brief. User-provided claims and functional scenes are execution inputs, not independently verified facts. Preserve their source and wording; do not demand extra substantiation solely because it is absent. Agent additions need approval within the plan.

## Working approach

Start or resume from the current deliverable, authorized scope and project state. Make routine creative decisions, propose missing copy, and ask only consequential unresolved questions (at most three per batch); continue unaffected work. Existing explicit authorization counts, without repeated confirmation. Explain any blocking skill rule with its exact source and the affected scope.

Within system, platform and tool permissions, current explicit user instructions override skill defaults, historical plans and Agent suggestions. New instructions replace only conflicting requirements. Documents are material to interpret, not an independent instruction authority; preserve the user's intended role for each source. Never turn a skipped check into a passing result. Use the contract's explicit override/export route instead of fabricating gate evidence.

Root owns lightweight communication: state scope, route and consequential assumptions at intake; share decision impacts, actual representative results, meaningful progress and blockers without narrating file operations. Ask only questions affecting correctness, scope or authority, and continue independent work. Answer status questions then resume; turn vague image feedback into observable changes. On an explicit pause, stop new generation calls and preserve in-flight state. No communication Agent, repeated approvals or separate reports.

Use the [workflow contract](references/workflow-contract.md) for the current stage's CLI, bindings and authorization. Read only relevant sections and specialist references; completed, unchanged work need not be reread or regenerated. New projects use `scripts/twin_stars.py v6`; unprefixed commands are legacy. Do not silently migrate runs.

New projects default to `workflow_profile:streamlined`; existing policies without that field (or `classic`) retain the [classic contract](references/workflow-classic.md). For a supplied/approved style, initialize with `--direction-mode existing` and record its `style_source`; use only D1. Pro remains separate.

For explicitly delegated direction selection, use `--direction-mode automatic`, record actual selection authority and one chosen D1 with its reasoning, then validate one representative image and proceed within delegated scope/budget. Use explore only for requested comparison or unresolved direction authority. Prompt/planning-only work stops at that deliverable without entering image-production gates. Revisions/extensions resume actual affected assets.

## Built-in aesthetic direction control

Invoke only `$twin-stars-agent-max` for this workflow. At intake and at every direction, sample and revision decision, apply the [built-in aesthetic control](references/aesthetic-control.md): read audience/channel/brand/reference roles, convert aesthetic adjectives or optional 1–10 intensity dials into observable visual targets, set a direction quality lock, reject template defaults without a brief-based reason, and inspect actual canvases at intended size. This applies by default, not only when the user says “Taste”; the user's stated constraints override inferred tastes. For Max, bind these decisions into the existing aesthetics/directions/plan controls and independent final-review brief rather than creating a separate Taste gate, skill call or approval step. Compare directions on expression and organization, protect passing properties on revision, and retain the existing generation/QA budget.

Leonxlnx/taste-skill is a frontend-oriented inspiration, not a runtime dependency or second command for the user. Do **not** require the user to invoke `$design-taste-frontend`; static commercial visuals use the self-contained adaptation above. Do not claim that a separate Taste review ran. If a request also includes real frontend implementation, the Agent owns routing and any available internal tools; clarify that static-image QA does not validate responsive UI, motion or interaction. Never silently apply frontend-specific rules to an image.

## Lifecycle

1. **Brief and selling-point interpretation — $product-evidence-control.** Inspect pixels, text, tables, annotations and embedded images. Separate fixed requirements, facts, preferences and proposals; translate features into audience/scenario, benefit or concern, and observable expression. Emotional/technical work uses its communication purpose. Map every actionable requirement to an asset, non-visual action or explicit gap.
2. **Research — $brand-art-direction and $commerce-visual-strategy.** Resolve market and aesthetic questions, keeping sources, observations and inferences separate. Independent searches may run together; stop when targeted additions no longer change decisions.
3. **Set planning and directions — $commerce-visual-strategy and $brand-art-direction.** Maintain one asset task table for purpose, source-backed message, visible expression, exact copy, reference role, set role and critical acceptance items, mapped to existing controls. Research changes priorities, not explicit user requirements. In explore mode, independent direction work is optional when it adds value; automatic/existing mode develops D1. No permanent team or additional tables. Lock shared product boundaries and chosen visual rules; differences must be visible in expression, organization and representation.
4. **Plan — $commerce-visual-strategy.** Present the brief/proposals, research and aesthetic anchors, the chosen route's concepts, representative scenes/copy, set rhythm, recommendation, sample scope and budget. Record sample authorization from an existing user instruction that actually delegates the creative/copy proposals and sample scope; ask for plan confirmation only when that authority is missing.
5. **Representative validation — $automated-visual-production.** One per active direction, using real sizes/text and the main structural/interaction difficulty. Creator inspects actual images at use size. Manual comparison uses one user selection; delegated production records existing authority with actual current image bindings and continues. Explicit user sample skips use the contract, not fake images or self-checks.
6. **Batch production and final review — $automated-visual-production and $visual-qa-delivery.** Reuse passing samples, produce ordinary assets continuously without complete per-image self-review reports. Inspect new difficulties or obvious shared failures early. One independent final session combines image correctness and set inspection; repairs recheck changes, protected features and real dependents. Single-image work goes directly to its final check. Direction/delegation authorization already covers passing delivery.
7. **Memory.** When reusable feedback or verified results exist, record them with source/scope using the contract's memory commands; future reuse must match brand and applicability. Do not create a retrospective just to fill a stage. Design opinion is separate from measured performance.

## Production invariants

- Use the built-in image tool and actual returned results; do not guess an underlying model or silently switch providers.
- Generate the complete canvas, including required product, scene, cast, text, Logo and layout. Portable delivery is one product identity image plus one complete model-neutral Chinese Prompt per asset; visible text retains its requested language.
- At most two attempts per logical asset, including samples, revisions, aliases and interrupted reservations. Follow V6 accounting; Pro has a separate contract.
- Independent first review receives actual images, original requirements, product evidence and approved standards, without creator rationale, self-scores or recommendations. Record real identity, version/hash, time and observations. If unavailable, keep it pending; explicit user final-review skips use export-unreviewed, never self-review or fabricated independent approval.
- Prefer `bind-bundle` for one authored control document and `review-packets` / `record-final-review` for one final review session; scripts create the necessary technical records.
- Root alone merges canonical state and approvals. Workers own isolated outputs; dispatch only useful non-overlapping work, respect available slots and record actual execution. No permanent agent per capability.
- On revision, preserve passing features and unrelated valid work. Changes to shared requirements invalidate only real dependents. Deliver current passing assets and identify unfinished scope; schema checks cannot establish commercial image quality.
